# Правила проекта «Цифровой деканат»

Прототип конкурса для студентов. Интерфейс русскоязычный. У команды два независимых агента и один репозиторий. Перед работой прочитай Issue или поручение, docs/CONTRACT.md и нужные строки docs/ACCEPTANCE.md.

## Границы изменений

- Одна задача — одна ветка от актуальной main и один небольшой PR. Капитан и напарник принимают работу и сливают ветки.
- Участник А ведёт серверный Python, миграции, модели и формы, конфигурацию, CI, инфраструктуру и серверные тесты. Участник Б ведёт templates/, static/, tests/ui/ и материалы интерфейса. Стартовая задача 00A может создать минимальные шаблоны, чтобы сервер запускался до интеграции.
- Согласовывайте изменения путей, полей и контекста шаблонов в docs/CONTRACT.md. В сообщении о таком изменении назови затронутые страницы и агента, которому нужно обновить код. Не переименовывай общий интерфейс молча.
- Общие зависимости и README запуска ведёт А. Если Б нужен инструмент экранного тестирования, зависимости для этого можно держать отдельно в tests/ui/. Материалы процесса храните по задачам в docs/evidence/<issue>/, чтобы два автора не перезаписывали дневник.
- Дай проверяемый результат. В PR перечисли что сделал, точные команды проверки, фактический результат, оставшиеся ограничения. При отсутствии окружения пометь отдельно, что ещё предстоит проверить.

## Решения по реализации

- Один Django-проект с серверными HTML-шаблонами, CSS и минимумом JavaScript. В публикации PostgreSQL с постоянным хранением. Для приложения достаточно одного HTTPS-адреса. Шрифты системные или поставляемые локально с лицензией. Для запуска кабинета жюри нужны только браузер и тестовый аккаунт.
- Используй штатные Django auth, хеширование паролей, серверную сессию, CSRF-защиту для действий и стандартное экранирование. Разрешения учитывают текущего пользователя на сервере при каждом обращении к закрытым данным. Для групповых занятий фильтруй по группе текущего студента. Отбор индивидуальных оценок, заявок и уведомлений — по текущему студенту. При выводе закрытых страниц учти выход из аккаунта и приватное кэширование.
- В опубликованной версии обязательны HTTPS, DEBUG=False, secure/HttpOnly для сессионной cookie, явные разрешённые хосты и секреты из окружения. Два обычных студенческих демоаккаунта получают разные вымышленные данные. У каждого отдельный пароль, переданный командой загрузки демоданных из окружения или безопасным вводом. Хостинговые ключи, пароли БД, содержимое .env и пароли студентов в исходники, скриншоты, логи и клиентский код не добавляй. В .env.example допустимы пустые имена переменных.
- Новая заявка получает статус «Принята» на сервере. Историческую «Готова к выдаче» можно подготовить заранее с пометкой демоданных. Статус новой заявки не меняется при перезагрузке страницы. Проверяй обязательные поля и защищай повторную отправку одной и той же формы от дублирования записи.
- Указывай «Конкурсный прототип · вымышленные данные» на входе и в доступном из кабинета месте. Используй собственное оформление и сохраняй источники и лицензии сторонних компонентов. Даты и время отображай по Москве.
- Ключевые экраны работают от 360 px, с клавиатуры и без горизонтальной прокрутки. Ошибка и смена статуса имеют текст, ссылки и кнопки осмысленные названия, поле формы — метку, клавиатурный фокус виден.
